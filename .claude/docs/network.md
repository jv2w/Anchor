# Network

Rules are in `.claude/rules/network.md`.

Packet formats and codecs are in `protocol.md`, every configuration key in `config.md`, dependency reviews and vendored copies in `dependencies.md`, bots and the official server comparison in `testing.md`.

## The UDP port (`udp.rs`)
- What `server-port` carries is in `config.md`. Both sockets on it (IPv4, IPv6-only) get 4 MiB kernel buffers: a burst from go-raknet's dialer, which has no congestion control, is several MiB. Linux caps the size at `net.core.rmem_max` without an error. A socket that cannot be opened stops the start with an error that names it (protocol, address, the settings that decide it, its use).
- The task reads at most 256 datagrams from a socket before it serves its other inputs, and runs both drivers' timers every 10 ms. The receive buffer is 2,048 bytes, larger than any datagram either transport accepts, so an oversized one is seen and dropped.
- Receive errors are skipped per datagram. Windows reports an ICMP port unreachable as WSAECONNRESET on the next receive; treated as fatal, one peer's ICMP reply would stop reading for the whole socket (tokio-rs/tokio#2017).
- Per-IP limits group by one IPv4 address or one IPv6 /64, the block one host is commonly given. An IPv4-mapped IPv6 address counts as its IPv4 address.
- The official server opens a game UDP socket per connection on increasing ports. Anchor shares one socket per address family between both transports, so a firewall or port forward needs one port, and one task holding both sockets and both drivers serves every connection without locks or copies between tasks.
- Datagrams are told apart by their first byte (RFC 7983): 20 to 63 is DTLS; 0 or 1 with the STUN magic cookie and a matching length is STUN; both go to NetherNet. The rest is RakNet. A datagram RakNet takes never starts with 20 to 63 or 0. Its unconnected ping, which starts with 1, passes as STUN only if the client's timestamp spells the cookie and the length; a client that crafts that loses only its own ping. A real ping is 33 bytes, a length STUN's 4-byte attribute padding never gives.
- Why TCP signaling stays: a client joining an address sends `GET /v1/join` to `https://host:port`, then `http://host:port`, uses the first that answers, and falls back to RakNet when both fail (go-nethernet `endpoint/handler.go`). The server list status is the JSON of that GET. The only UDP-only way to reach NetherNet is LAN discovery (UDP 7551), which Anchor does not implement.

## NetherNet
The answers match, byte for byte in structure, what the official server sends with `transport=nethernet` (its version is in the pinned-source table of `data.md`).

### Signaling (`nethernet/signaling.rs`)
- A minimal HTTP/1.1 server: one request per connection attempt, no trickle ICE. Only GET and POST are routed.
- `GET /v1/join`: 200, `application/json`, body keys in the order `name, protocol, version, level, players, maxPlayers, gameType`.
- `POST /v1/join/{networkId}`: the body is the SDP offer and the answer is the SDP answer, `application/sdp`. A failed negotiation is HTTP 200 too, as on the official server, with the error code in decimal as the body: `37` identity failure, `13` unusable offer (an empty or non-UTF-8 body, a malformed SDP, or an `a=identity` value that breaks the shape and size rules below: go-nethernet parses it with the rest of the offer), `11` internal failure (no UDP socket of the address family to advertise, ICE ufrag collisions, the peer or the answer could not be made, the driver gone). The log gives the cause of every refused offer: debug for the client's offer or identity, warn for an internal failure.
- Refusals carry their reason phrase as a `text/plain` body. 404 `Not Found`: an unknown path, or a known path with another method. 400: a malformed request, a network ID that is not 1 to 20 decimal digits, `Content-Length` together with `Transfer-Encoding: chunked` (the request smuggling shape, RFC 9112), or chunked on HTTP/1.0. 431: a head over its limit. 413: a body or chunked framing over its limit. 503: over the connection limits (on plain HTTP only; a TLS client sees only the close), a full offer queue, or too many peers before login. Every response has `Connection: close`, and the connection closes after it.
- Limits: 64 open connections, 4 per IP, a head of 8 KiB, a body of 64 KiB after chunked decoding, 8 KiB of chunked framing, 10 seconds per connection from accept to close (TLS handshake, reading, negotiation, writing). A connection past its deadline is dropped without a response.
- Trust: plain HTTP by default, and the client asks the player to confirm a server key it has not seen (trust on first use). With `nethernet-tls-cert` and `nethernet-tls-key` (PEM, at most 1 MiB each) signaling is HTTPS (tokio-rustls, aws-lc-rs provider). Without TLS, a first byte of 0x16 (a TLS ClientHello) gets a fatal `handshake_failure` alert and the close, as on the official server, so the client gives up on https at once and tries http.

### SDP (`nethernet/sdp.rs`)
- Offer limits and rules: at most 64 KiB and 1,024 non-empty lines, no control characters, first line `v=0`, exactly one media section `m=application <port> UDP/DTLS/SCTP webrtc-datachannel`. Required once each: `ice-ufrag` (4 to 256 ICE characters), `ice-pwd` (22 to 256), `fingerprint` (one `sha-256` digest of 32 bytes), `setup` (`actpass` or `passive`), `max-message-size` (at least 1,024). `sctp-port`, when present, is 5000. At most 32 usable candidates: UDP, component 1, an IP literal address; others (TCP, mDNS names) are skipped. go-nethernet writes the candidate line as `candidate:candidate:...`, so the prefix is accepted once or twice. `a=identity` is accepted only at the session level.
- Answer lines, in the official server's order: `v, o, s, t, a=group:BUNDLE 0, a=extmap-allow-mixed, a=msid-semantic: WMS, a=identity, m=application <port> UDP/DTLS/SCTP webrtc-datachannel, c, a=candidate (host), a=ice-ufrag (4 characters), a=ice-pwd (24 characters), a=ice-options:trickle, a=fingerprint:sha-256 <uppercase hex>, a=setup:active, a=mid:0, a=sctp-port:5000, a=max-message-size:262144`. There is no `a=end-of-candidates`. The `o=` session ID is random per answer. The candidate's foundation is the decimal CRC-32 of `"local" + ip + "udp"`, its priority 2122260223 (the official server's value), and it ends `generation 0 network-id 1`.
- Advertised address: `public-ip` when set, otherwise the local address of the signaling TCP connection the client reached (the standard library cannot list interfaces, and the client certainly reaches this address). An IPv4-mapped IPv6 address is written as IPv4. The port is the `server-port` UDP socket of that address family; without one, code 11.

### Identity (`nethernet/identity.rs`)
- The offer's `a=identity`: padded standard base64 of at most 32 KiB of JSON, `{"assertion":"<JSON text of {fingerprints, token}>","idp":{"domain":..,"protocol":"default"}}`, with a domain of 1 to 256 bytes. `token` is a compact JWS no longer than the longest Login token; `fingerprints` is a detached ES384 JWS (at most 1,024 characters) by the token's `cpk` over `{"fingerprint":[{"algorithm":"<as in the SDP>","digest":"<as in the SDP>"}]}`. Online, the token follows the Login `Token` rules (below); offline, it is read without its signature: `alg` must be ES384 or RS256, and `exp`, `nbf`, `iat` hold when present. Online, `cpk` is a base64 SPKI string (the Login rule); offline it may also be a P-384 JWK object. A value that breaks the shape and size rules fails the offer's parse (code 13); a failure to verify is code 37.
- An offer without an identity: the official server refuses it with 37 even offline. Anchor accepts it offline for custom clients.
- The answer's `a=identity`: without it the client rejects the answer. It sits at the session level (before `m=`), and its value is padded standard base64 of `{"assertion":"{\"fingerprints\":\"<detached JWS>\",\"token\":\"<JWT>\"}","idp":{"domain":"self","protocol":"default"}}`, keys in that order.
  - Server JWT: header `{"alg":"ES384","x5u":"<base64 SPKI>"}`, payload `{"cpk":<JWK>,"exp":<iat + 60>,"iat":<now>}`, each JSON followed by a line feed, the JWK keys in the order `crv, kty, x, y`. The official server and Mojang's guide also write `cpk` as a JWK object. As on the official server, a new token is issued per answer and lasts 60 seconds.
  - Detached JWS: header `{"alg":"ES384"}`, signing `{"fingerprint":[{"algorithm":"sha-256","digest":"<as written in the SDP>"}]}`.
- The server identity key `data/identity.key`: P-384 PKCS#8 DER, read only up to 4 KiB, once at start on the blocking pool. A new key makes every player confirm the server again.
- Identity binding: an offline offer without an identity has nothing to bind. The official server accepts, offline, a Login key that differs from the offer's `cpk`; Anchor disconnects because the identity proved at signaling and the identity in the game must be the same.

### Peers (`nethernet.rs`, `nethernet/peer.rs`, `nethernet/message.rs`)
- The driver runs in the UDP task beside RakNet's. A STUN binding request finds its peer by the server ufrag in its USERNAME; any other datagram by its source address. Both indexes are `BTreeMap`s. A new source address joins a peer only through a STUN request with that peer's ufrag, at most 8 per peer, and never one another live peer holds: a client knows its own ICE credentials, so its valid STUN request can carry any spoofed source. A separate offer task parses each offer, asks the driver whether the pre-login limits have room for its IP, and only then verifies it and asks the driver for a peer (the driver checks the limits again). A peer whose offer task is gone before the answer is removed at once.
- One str0m `Rtc` per peer, without sockets. The server is ICE controlled, DTLS client (`setup:active`), and SCTP client, the official server's roles, on DTLS 1.2. One DTLS certificate (self-signed ECDSA P-256 through str0m's aws-lc-rs provider) is made at start, so no peer pays for key generation and no join pays for lazy setup. The ICE ufrag (4 characters, 24 random bits) and password (24 characters) come from the `crypto` randomness; a ufrag another peer uses is drawn again, and the third collision in a row is code 11.
- Channels: the client opens `ReliableDataChannel` (ordered, reliable) and `UnreliableDataChannel` (unordered, maxRetransmits 0). A channel with another label or parameters, or a channel opened twice, closes the peer. Messages on the unreliable channel are read and dropped, counted at trace: only the official client knows their content, so every case is accepted. go-nethernet sends before it sees the channels' open acknowledgement, so reliable messages that arrive before the unreliable channel opens are held, up to one largest message in bytes, and handed over once both are open.
- Segments: each data channel message starts with one byte, the number of segments after it, so a message has at most 256. Sent segments carry `min(remote max-message-size, 262,144) - 1` payload bytes, 262,143 as on the official server. Received segments may have any non-empty size (go-nethernet sends 65,535 bytes). A wrong count, an empty segment, or a message past the reassembly limit closes the peer. The reassembly limit is the message limit under Compression, without 0xfe or a checksum.
- str0m's direct API cannot take the remote `max-message-size`, so the remote values go in through its SDP API. Were the client's `actpass` written in that internal offer, str0m would take the DTLS server role, unlike the official server.
- Deadlines: 10 seconds from the peer's creation until both channels are open; once open, 10 seconds without a datagram str0m accepts. pion sends an ICE keepalive every 2 seconds and str0m checks the nominated pair at least every 3 seconds, so this is three missed rounds. str0m alone never gives up: its ICE only reports `Disconnected` and its SCTP retransmits forever.
- Close: a closed connection's peer stays until SCTP has acknowledged everything sent, or 5 seconds, so the last Disconnect reaches the client. At shutdown, peers without a connection go at once.
- Limits: 8 source addresses per peer, datagrams of at most 1,500 bytes whose first byte is 0, 1, or 20 to 63, an inbound queue of 1,024 messages and 2 × the message limit in bytes, 32 MiB of bytes not yet sent, an SCTP send buffer of 1 MiB (four largest messages; str0m's 128 KiB default cannot take a 262,144-byte message), a command queue of 4,096, an offer queue of 64.
- Ping: SCTP's RTT is not exposed, so the ping is the RTT of the latest ICE consent check (RFC 7675) on the selected pair, reported every 2 seconds.
- Isolation: str0m and its DTLS and SCTP crates can still panic. Guarding each peer's str0m calls applies the `CLAUDE.md` rule that a connection task's panic ends only that connection to the peers sharing one task. A peer that panicked is never touched again; dropping one runs no str0m code (no `Drop` in str0m, str0m-proto, str0m-aws-lc-rs, dimpl, or sctp-proto).
- Cost, measured with `driver_cost_per_peer`: 3.55 ms per MiB sent, 2.91 ms per MiB received; one player (50 KB/s down, 5 KB/s up) about 0.53 ms per second; one join (2 MiB) about 16 ms. One task serves about 500 players.
- NetherNet has no Minecraft encryption (DTLS encrypts) and no 0xfe byte; the batch bytes, compression header included, are the same.

## RakNet (`raknet.rs`, `raknet/`)
- The sans-IO core (`wire`, `peer`, `listener`, without sockets or clocks) handles the offline messages, the connection table and its limits, sequence numbers, reliability, ordering, splitting, ACK and NAK, resends, and congestion control. The driver feeds it the datagrams the UDP task hands over and the time.
- Only RakNet protocol 11 is accepted; any other gets IncompatibleProtocolVersion. The MTU a client probes is its padded OpenConnectionRequest1 plus 28 header bytes; below 400 it gets no reply. The connection's MTU is min(request, `max-mtu-size`). A client GUID must be negative, as vanilla clients send.
- Why no cookie (security): the official server answers with security off, and the official client's cookie handling cannot be observed. Spoofed sources are bounded only by the pre-login limits and the handshake and idle deadlines.
- Constants (canonical in `src/raknet/`, except the pre-login limits and the unsent-bytes cap that both transports share, which are in `src/raknet.rs`; the socket buffer and the 10 ms update in `udp.rs`): fragments per message at most ⌈message / smallest full fragment⌉ (a 400-byte MTU datagram without its headers), 16 split messages reassembled at once, an order window of 2,048 (32 channels apart), 1,024 datagram numbers remembered (a number 1,024 or more ahead of the next one expected drops that datagram only and does not count as heard; a second one within 1,024 numbers after it moves the record there, because a sender that lost 1,024 datagrams in a row, as a burst past a slow link's queue can, sends its resends under new, further numbers and would never be heard again), 8,192 reliable index gaps, held bytes (reassembly and ordering) 2 × the largest message plus a full send window, but only 4 largest datagrams until NewIncomingConnection, a congestion window of 32 (4 to 2,048, × 3/4 once per round of losses), an RTO of 500 ms before the first sample (100 ms to 2 s; doubled once per round of losses a timeout starts, never for a NAK, and reset by the next RTT sample; the peer's 100 ms ACK delay is added in place of a smaller variation term), ACKs sent every update or at 64 pending ranges, at most 32 datagrams per flush, 32 MiB outbound, an inbound queue of 1,024 messages and 2 × the message limit in bytes, a 10 s handshake (OpenConnectionRequest2 to NewIncomingConnection), a connected ping every 500 ms (sent at once, outside the send queue and the congestion window, like the pong to the client's ping and the disconnect notification, so waiting reliable data neither drops nor delays it), an idle timeout of 5 s + 2 × RTT, a 5 s graceful close, pong data of at most 1,429 bytes. The message limit is the reassembly limit under Compression plus 9 bytes (0xfe and the 8-byte checksum).
- An ACK or NAK that cannot be read is dropped as that datagram only: nothing authenticates a datagram, so it never closes the connection and never counts as heard.
- From OpenConnectionRequest2 until the session logs the player in, past the pre-login limits, the reply is 0x14 (NoFreeIncomingConnections).
- Ping: a token bucket per IP (5 per second, bursts of 10). At most 4,096 IPs are tracked, an entry is dropped after a minute without pings, and while the table is full pings from new IPs get no reply. The pong uses the official server's layout `MCPE;motd;<protocol>;<game version>;<players>;<max>;<guid>;<level>;<mode>;1;<port>;<port>;0;1;1;` (numbers and versions in `protocol.md`). Fields are split at `;`, so a `;` or control character in `motd` or `level-name` would break it.
- The official server logs on its RakNet transport that players cannot connect without NetherNet. Whether the official client still joins over RakNet is unverified. Either way RakNet is needed as the fallback and for custom clients.

## Sessions (`session.rs`, `session/`)
- The session carries both transports through one flow with the `Transport` enum (`Raknet`, `Nethernet`).
- A session that ends tells the tick why in its Leave input: RakNet's disconnect notification and NetherNet's remote close are `Left`, a silent connection is `TimedOut`, and everything else (a session failure, a transport close, a deadline) is `ConnectionClosed`. A kick, transfer, replacement or shutdown is decided by the tick.
- Order: RequestNetworkSettings → NetworkSettings (compression) → Login verification → ServerToClientHandshake and, on RakNet only, encryption on → ClientToServerHandshake → PlayStatus(LoginSuccess) and ResourcePacksInfo (one batch, this order, as on the official server) → (when the client lacks packs) response SendPacks → ResourcePackDataInfo and the chunks asked for → response AllPacksDownloaded → ResourcePackStack → response Completed → the tick's Join → the StartGame packets → RequestChunkRadius → ChunkRadiusUpdated, chunks, PlayStatus(PlayerSpawn) → SetLocalPlayerAsInitialised. NetherNet also sends ServerToClientHandshake but never turns encryption on, as the official server does.
- RequestNetworkSettings is the only message without a compression header; it must be at most 1 KiB and hold that one packet. Login must be the first packet of the first compressed batch; the rest of that batch is handled after the verification, except on an encrypted RakNet connection, where a packet after the Login ends the session: encryption starts with the next message, so a plain packet after the Login would pass without the proof that the client holds its key (gophertunnel sends the Login alone).
- A different protocol number (in RequestNetworkSettings or Login) gets PlayStatus LoginFailedServer when the client's is higher, LoginFailedClient when lower, then the disconnect.
- The deferred queue before the join holds 32 packets and 1 MiB (`MAX_DEFERRED_BYTES`, each packet counted as the input log counts it); more disconnects. Packets are deferred because gophertunnel defers them too and the official client's order cannot be observed. Chunks are sent without the blob cache, so ClientCacheStatus needs no reply and is dropped.
- A decode failure after the spawn drops only that packet because no one can observe every case of the official client's output, so the receiving side is lenient. A packet whose ID only servers send (not in gophertunnel's client packet pool) counts as one that fails to decode.
- Deadlines: 10 seconds from the connection to a verified Login, 60 seconds to SetLocalPlayerAsInitialised. A pack download moves the spawn deadline by 30 seconds once plus 2 seconds per chunk sent (a floor of 64 KiB/s). After the join, each batch the tick sends up to the one with PlayStatus(PlayerSpawn) moves it at the same rate (2 seconds per 128 KiB) as it is handed to the transport, because the two PlayerLists before the spawn grow with players × skin size. Batches after that one move nothing. The total extension is at most the time two PlayerLists of `max-players` (at start) players with the largest skins take at that rate; the base 60 seconds cover the rest. So a client that keeps receiving broadcasts but never spawns, even one never sent PlayerSpawn (it sends no RequestChunkRadius, or a send hook drops the packet), still times out.
- Pack chunks are 128 KiB. The next one goes out once 200 ms have passed since the last and the connection has at most one chunk (128 KiB) not yet delivered. Undelivered bytes are, for RakNet, those queued or unacknowledged (reported every 10 ms update), for NetherNet, those in the peer's queue and SCTP buffer (reported whenever the peer is polled); the session reads them from a watch, as it reads the ping. A client may request every chunk at once, and pacing by time alone would pass the 32 MiB outbound cap on a slow link; waiting for delivery keeps about two chunks in flight.
- Output:
  - The session takes the tick's messages as they come and queues them in order. Its own packets are batched as they are taken. A shared packet (a broadcast, or a spawn window's PlayerList: the tick marks the two, one with StartGame, one in the spawn window) is batched and compressed by the first session that takes it, into batches of its own; every other session that takes it waits for those batches (an async cell, so no thread waits) and shares them, so a skin or a PlayerList of every skin costs one compression whatever the receivers. Every joined session compresses with the server's batch settings, so the first session's batches are those every other would make. A send hook's changed copy starts without batches. The shared batches, and the shared start batches, wait as the shared copy and are copied when their turn comes. This holds whatever the spawn state.
  - The next batch goes to the transport only while the connection's undelivered bytes (the watch above, plus what was handed over in the last 30 ms: both transports take messages as they come and report every 10 ms update, so later counts include them) are at most 4 MiB. Output is handed over in parts because a PlayerList with many large skins, or many join notices in one tick, can pass 32 MiB; handed over at once it would hit the transport cap whatever the link speed. 4 MiB is above what either transport keeps in flight (RakNet's 2,048-datagram window of 1,492 bytes with its frame cost, about 3.1 MiB; NetherNet's 1 MiB SCTP buffer), so a healthy link is never throttled, and with one more batch of the default 16 MiB `max-batch-bytes` (at most 18.7 MiB compressed, plus about 4.7 MiB of RakNet frame cost at the smallest MTU) it stays under the transports' 32 MiB caps, past which they disconnect. Sequence and encryption counters follow the handover order.
  - When the waiting bytes (batched bodies and shared batches; everything but the spawn windows' PlayerLists) pass 32 MiB, the session ends. A slow link thus ends on the bytes waiting, not on time or on the tick's message count, and the tick's outbound queue fills only when the session task falls behind. The spawn windows' PlayerLists stay uncounted shared copies because they grow with players × skin size, so a per-session copy or a byte count would pass any bound; a session gets only those two, so the uncounted amount is bounded. The shared start batches are fixed at start and need no copy, but their bytes count. Broadcasts are counted by the bytes of their batches when taken because they keep coming to clients that never got the spawn status, and uncounted they would grow with time; small shared packets (soft enum updates, join notices, skins) end the session on bytes, not on count. The cost: a slow client behind an undelivered PlayerList that collects over 32 MiB of broadcasts ends before it spawns.
  - The tick's last packet (Close) and the shutdown message go out apart from this: everything waiting is handed over at once, then the last packet, because the session ends right after and the last packet must follow the earlier output.
- Connection limits: before login, 64 per transport and 4 per IP (128 in total). The accept queue holds 64 new connections per transport; when it is full, the newest closes. A verified login gives its pre-login slot back, and logged-in sessions that have not joined are counted by a semaphore of `max-players` (at start); none left gets PlayStatus server full, and one IP (by `raknet::ip_key`) holds at most as many of those places as it had pre-login slots. After the join the tick decides with `max-players`.
- Input budget: per session, a token bucket of decompressed bytes (capacity `max-batch-bytes`, refilling `max-batch-bytes` / 4 per second) and one of packets (capacity 1,024, the session's share of the tick queue; 512 per second). Bytes are charged per batch, and what decoding a packet allocated beyond its own bytes is charged when it decodes (a packet of few bytes can decode into far more); packets are charged one by one before decoding, so dropped packets count too.
  - The held click: a copy of the last forwarded right click held on a block (InventoryTransaction UseItem ClickBlock, trigger `SimulationTick`) with the same header and bytes, within 25 ms (half a tick) of it, is dropped without being charged to the packet bucket or decoded; its bytes are charged. Forwarding any other use (another InventoryTransaction, a PlayerAuthInput with an item interaction) forgets it. The official client sends this click every frame while the button is down (`xtask/data/p6/facts.md`: about 20 per tick at 600 fps; the official server's `packetlimitconfig.json` has no InventoryTransaction group). Frame rates have no bound, so any count limit would disconnect some honest client.
  - Where the drop can change the tick's result: the tick ignores an identical click for two ticks from the first one it applied (`tick/interact.rs`), so it would have ignored most dropped copies, but the two windows start at different points (the tick at the first applied click, the session at the last forwarded copy). With evenly spaced copies, frames over 25 ms apart drop nothing, and frames 25 ms apart or closer forward a copy within 50 ms of the last, so one reaches every tick and the click applies in the same tick. The copy applied may be a later one, though, so its order against the session's other packets (a PlayerAuthInput with only movement, an ItemStackRequest) can change. Copies bunched by network jitter can delay the click by one tick.
  - Each LevelChunk the session sends in sub-chunk request mode gives the packet bucket one packet back (up to its capacity): the client answers each such chunk with a SubChunkRequest, which the server asked for. The tick answers up to 256 requests per player per tick (the top of `chunks-per-tick`) holding up to 8,192 offsets in all (each offset is an answer entry with its own copy of the sub-chunk; a request holds 8,192 at most), and holds up to twice each, so honest requests (for the 24 sub-chunks of each chunk sent, 6,144 a tick at the largest setting) are neither cut off nor dropped even at the largest setting, while one client's requests of 8,192 offsets each queue no more than two ticks of answers.
  - At the default `max-players` of 20, the sessions' 10,240 packets per second plus the chunk requests (`chunks-per-tick` × 20 ticks × 20 players, at most 102,400) stay below the 163,840 per second (8,192 per tick) the tick applies. The values are generous: a client sends one PlayerAuthInput per client tick (20 per second) and a few packets per action, and bot captures carry no timestamps to measure a peak per second. The burst is above the 812 packets one batch may hold.
- Tick input queue shares: per session, at most 1,024 inputs the tick has not taken; only a session over its share ends. The queue is sized at start to (2 × `max-players` + 3 engine sessions) × 1,024 + 1,024 job results, so every share always fits and a session filling its share never ends another. A connection session holds a share from its join until the tick takes its leave (`max-players` online, and as many whose join the tick has not applied, or has refused but whose leave it has not taken); with every share held, the join gets server full. The queue is in order, so when the tick takes a leave it has taken every earlier input of that session, and reconnecting over and over never holds more than shares × 1,024 connection inputs. A leave waits for room in its own share. With many sessions at their full share, an honest input waits at most (those sessions × 1,024) / 8,192 ticks.
- The shutdown grace for sessions is 10 seconds.
- A second login of the same player: the same player is the same XUID online, the same name ignoring ASCII case offline. The tick's join raises `PlayerDuplicateLogin`. Not cancelled, the new connection is first checked like any login (`PlayerLogin`: full server, counting the slot the replacement frees; whitelist; bans; listeners); once it is admitted, the existing player is disconnected with LoggedInOtherLocation (default message `disconnectionScreen.loggedinOtherLocation`) and the new one joins. Refused, only the new connection goes and the existing player stays, so one refused login never costs an honest player. Cancelled, the new connection goes with the same packet. It is decided at the join because game state and user callbacks live only in the tick; deciding at login would add a round trip between the session and the tick. The official server renames the new connection to `name(2)`.
- An admitted player waits for its saved data before it is placed. When the data arrives, a ban or a whitelist change made since its login refuses it, as the login would have, with the data left as saved: the commands and calls that kick the players such a change leaves out see only players in the game. A refusal a `PlayerLogin` listener cleared stays cleared, and a full server is not asked again (the player holds its slot).

## Login and authentication (`login.rs`, `auth.rs`, `auth/`)
- Online (`xbox-auth = true`): only the Login `Token` (the OIDC multiplayer token) counts; the legacy chain is ignored. RS256 only; `kid` and `exp` required; `nbf` and `iat` checked when present; 60 seconds of clock skew. `iss` must equal the OpenID configuration's `issuer`, and `aud` must contain `api://auth-minecraft-services/multiplayer`. `xid` is decimal digits fitting an `i64`, `xname` is not empty, `cpk` is a base64 P-384 SPKI. The online name is not checked further.
- Offline (`xbox-auth = false`): with a `Token`, its claims are read without verification (ES384 or RS256); without one, the legacy chain (1 or 3 ES384 links, the first self-signed through `x5u`). The XUID is always empty. Name rule: 1 to 16 bytes of `A-Z a-z 0-9 _` and space, and not `rcon` or `console` in any case.
- Guest authentication (`AuthenticationType` 1) is refused, as in gophertunnel.
- The player UUID: the token's `leguuid` when it has one; otherwise, online, one made from the XUID; offline, one made from the XUID, or from the name when there is no XUID. A legacy chain gives the client's `identity`. An offline UUID is the client's claim.
- ClientData: only its ES384 signature by `cpk` is verified. Its content is checked with gophertunnel's `ClientData.Validate` rules, with their defects fixed. The JSON is strict (case-sensitive names; null and duplicate keys rejected). The texts the player keeps are bounded: `DeviceId` and `DeviceModel` 256 bytes, `GameVersion` 32, `ServerAddress` 512.
- JWT time checks run off the tick, so they read the wall clock.
- Limits: chain JSON 64 KiB, a token or chain link payload 16 KiB, 8 chain links, 16 `aud` entries, RSA moduli of 2,048 to 4,096 bits, 64 JWKS keys.
- Authorization environment: the service discovery (`https://client.discovery.minecraft-services.net/api/v1.0/discovery/MinecraftPE/builds/<game version>`) gives `auth.prod`'s issuer, whose `/.well-known/openid-configuration` gives the JWKS URI. One fetch (all three requests) must finish within 10 seconds (DNS lookups bounded only by the OS), and each response body is under 1 MiB (ureq refuses one of exactly that size).
- The cache `data/auth.json` holds the OpenID configuration, the JWKS, and when they were fetched (discovery is only used to find the OpenID configuration). At start, a cache younger than an hour is used as is; otherwise everything is fetched, falling back to the cache on failure; with neither, the server does not start. A cache that is not the expected JSON, holds unusable keys, or is over 1 MiB is corrupt. While running, everything is fetched again every hour. The interval between JWKS fetches for unknown `kid`s keeps forged `kid`s from multiplying outside requests.

## Encryption (`crypto.rs`, `crypto/`)
RakNet only.
- The server key is one new P-384 key per run, for both signing and ECDH; the salt is 16 random bytes per connection, sent in the ServerToClientHandshake ES384 JWT.
- key = SHA-256(salt ‖ ECDH-P384 shared secret). AES-256-CTR with IV = key[0..12] ‖ 00000002, one continuous stream per direction, over everything after 0xfe (gophertunnel's comment says CFB8; its code uses CTR).
- Checksum = the first 8 bytes of SHA-256(LE64(counter) ‖ plaintext ‖ key), with separate send and receive counters. A mismatch disconnects.
- The `crypto` module wraps aws-lc-rs.
- With `enable-encryption = false`, a RakNet login skips ServerToClientHandshake and encryption and goes straight to LoginSuccess.

## Compression (`protocol/batch.rs`, `protocol/compression*`)
- The threshold 256 is gophertunnel's and Java Edition's default; in measurements, batches of about 100 bytes grew when compressed. The threshold is announced in NetworkSettings.
- Format: NetworkSettings compression ID 0 is zlib, 1 Snappy. A batch's first byte is 0x00 for zlib, 0x01 for Snappy, 0xff for uncompressed (below the threshold). Any first byte other than the negotiated ID and 0xff disconnects. zlib is raw DEFLATE without a header; input after the final block is ignored, since only the official client shows whether its encoder leaves any. Snappy is the block format: offset 0, an offset before the output, output past the declared length, input after the stream, and output shorter than declared are errors; copy-4 is accepted. Unlike gophertunnel, no S2 extension (`protocol.md`).
- Why a 16 MiB decompression limit: honest Logins over 2 MiB are common, and the official server sends a batch of about 9 MB when it returns large skins in PlayerList. Why 22 times for Snappy: a valid stream grows at most 64 bytes per 3-byte copy.
- Before login: Login is the largest honest batch, so the decompression limit stays. A NetherNet message before login is at most `MAX_PRE_LOGIN_MESSAGE_BYTES` (`src/nethernet.rs`), which holds a Login with the largest skin; the full limit applies from the login on. Also, the message before NetworkSettings is at most 1 KiB, the first batch's first packet must be Login, and the reassembled plus decompressed bytes of a session before login verification total at most 8 × `max-batch-bytes`.
- Reassembly limit: one message is at most `max-batch-bytes + max-batch-bytes / 6 + 42` bytes (Snappy's worst case and the header byte). RakNet's fragment limit is this divided by the smallest full fragment. A RakNet connection holds at most four datagrams of reassembly until NewIncomingConnection and, until the session logs the player in, the limits of a message of `MAX_PRE_LOGIN_MESSAGE_BYTES` (the same cap as NetherNet's pre-login message); the full limits apply from the login on.
- Where outbound batches are cut (size and count) is in `protocol.md`'s batch format. Order is kept.
- The Snappy format on the server side is confirmed against the official server.

## Behavior only the official client shows
Neither the official server nor bots can settle these.
- Whether the official client joins over RakNet.
- gophertunnel's comment reports, unconfirmed, that devices without AVX2 crash with Snappy (a Mojang bug report points the same way).
- Whether a held right click's copies stay byte-identical within a client tick while the player moves, and whether other packets come every frame. If the position changes every frame, the copies cannot be dropped and count against the packet budget, so a client holding the button while moving at over 512 frames per second exceeds it and is disconnected. Copies do count against the byte budget, so holding a heavy item (NBT of a few KiB) at hundreds of frames per second can reach `max-batch-bytes` / 4 per second.
- Whether 32 deferred packets before the join are enough, whether the strict ClientData JSON accepts all of the official client's output, and the number after a mode other than survival in the pong (the official server sends only `Survival;1`).
- The content of the unreliable data channel, and whether the official client's NetherNet sends ICE consent checks that give a ping.
- Whether the official client accepts a RakNet login without encryption (`enable-encryption = false`).
- Windows cannot flush a folder (`storage.md`). A newly created `identity.key` lost to a power cut is created again at the next start.
- dimpl and sctp-proto log through `log`, so a binary that only uses `tracing` does not see those records; the user's binary can add a bridge if needed.
