# 프로토콜

Anchor의 패킷 코덱은 고정한 gophertunnel에서 뽑은 IR로 생성한다. 이 문서는 정답 출처와 고정 버전, IR에서 생성 코드까지의 파이프라인, 디코드 상한, 시험 P1~P5, 버전업 절차를 적는다. 전송, 로그인, 암호화, 압축은 `network.md`, BDS 대조(P6)는 `testing.md`, 블록과 아이템 데이터는 `data.md`, 외부 불신 절차와 의존성 검토는 `dependencies.md`에 있다.

## 한 번에 한 버전
- 한 번에 한 프로토콜 버전만 지원한다: 프로토콜 2193, 게임 버전 1.26.50(`protocol::packet::PROTOCOL_VERSION`, `GAME_VERSION`). 여러 버전을 함께 받으면 코덱, 블록 표, 시험이 버전 수만큼 늘어나 일관성과 단순함을 잃는다.
- 다른 번호의 클라이언트는 RequestNetworkSettings(또는 Login)에서 PlayStatus(클라이언트가 높으면 서버 구버전, 낮으면 클라이언트 구버전)를 받고 끊긴다.
- 버전을 올리는 것은 공개 API의 깨지는 변경으로 다룬다(semver).

## 정답 출처와 고정 버전
- 프로토콜 정답은 sandertv/gophertunnel과 그 go.mod가 고정한 go-raknet, go-nethernet이다. Go 쪽 버전은 `xtask/go/go.mod`에 의사 버전으로 고정하고, IR(`xtask/data/protocol.json`)의 `source`가 같은 값을 적는다.

| 모듈 | 고정 버전 |
|---|---|
| github.com/sandertv/gophertunnel | `v1.62.1-0.20260928233358-80c811b61860`(커밋 `80c811b6186016b3860c358368cfa47e507f26e9`, v1.62.0 뒤 19커밋, 프로토콜 2193, 1.26.50) |
| github.com/sandertv/go-raknet | `v1.15.2-0.20260705184311-0d1fd09e2cf6` |
| github.com/df-mc/go-nethernet | `v1.0.20-0.20260818142457-6fc1eb6f907c` |
| Mojang bedrock-protocol-docs(필드 상한) | 커밋 `475bd72ed89036af4eb18426774ef3b953de7603`(v1.26.50 릴리스, 프로토콜 2193) |

- 고르는 규칙: gophertunnel의 최신 정식 태그다(프리뷰 브랜치는 쓰지 않는다). 태그 뒤 master에 같은 프로토콜의 형식 수정이 있으면 그 커밋으로 고정한다. 지금 고정한 커밋은 v1.62.0 뒤의 형식 수정 ClientBoundDebugRenderer(`98c3d1f`), NBT 고정 길이 배열 검사(`398154f`), 문자열 `ReadFull`(`a705cae`)을 포함한다.
- 블록과 아이템의 종류와 동작은 PMMP가 정답이다(`data.md`). 기준 서버는 같은 프로토콜의 BDS 1.26.52.3이다. BDS의 빌드 번호는 1.26.52이고 Anchor는 프로토콜 출처의 1.26.50을 알리지만 둘 다 2193이다.
- gophertunnel도 형식 버그를 자주 고친다. P3 통과는 "gophertunnel과 같다"는 뜻일 뿐이다. BDS 대조(P6)와 다르면 BDS를 따르고 외부 불신 절차로 처리한다(`dependencies.md`).
- `/versionup`과 BDS 실행 파일 분석은 쓰지 않는다. 사실의 근거는 gophertunnel 코드, Mojang 문서, BDS를 실행해 봇으로 관찰한 값뿐이다.

## 파이프라인: Go 추출 → IR → Rust 생성

```
gophertunnel 소스 ──(xtask/go/extract)──> xtask/data/protocol.json ──(cargo xtask gen)──> src/protocol/{types,packet,consts}.rs
Mojang 스키마 ──(cargo xtask dump)──> xtask/data/reference/protocol_limits.json ──┘
```

### 추출기 (`xtask/go/extract`)
- `golang.org/x/tools/go/packages`로 타입 정보까지 읽고, 각 패킷과 타입의 `Marshal(io protocol.IO)`를 걸어 IR을 낸다. 모르는 구문이 하나라도 있으면 실패한다: 조용히 건너뛴 필드가 틀린 코덱이 되는 것을 막는다.
- 주석은 읽지 않는다. 생성 코드의 문서는 생성기가 IR의 자기 정보로 쓴다(gophertunnel 주석을 옮기지 않는다).

### IR (`xtask/data/protocol.json`, 커밋한다)
- `source`: 모듈, 의사 버전, 커밋, 프로토콜 번호, 게임 버전.
- `packets`: ID, 이름, 방향(gophertunnel `pool.go`의 클라이언트·서버 풀). 236개.
- `types`: 필드 이름, Go 타입, Marshal 문장 목록. 문장은 IO 호출, 중첩 Marshal, 목록(길이 형식 포함), Optional, if, switch, 지역 변수, 대입, 오류(`InvalidValue`, `UnknownEnumOption`)뿐이다.
- `io_methods`(`protocol.IO`의 메서드), `functions`(IO를 받는 자유 함수), `unions`(`lookup*` 함수의 ID→타입 표), `enums`(문자열↔값 변환 함수 표), `constants`, `const_decls`(protocol·packet 패키지의 export 상수).

### 생성기 (`cargo xtask gen`, `xtask/src/gen*`)
- `gen`은 Go 추출 → IR → Rust 생성을 한 번에 한다. 출력은 `src/protocol/types.rs`(gophertunnel `protocol` 패키지 타입), `src/protocol/packet.rs`(패킷, `Packet` enum, `PROTOCOL_VERSION`), `src/protocol/consts.rs`(IR 상수에서 만든 enum과 상수. 쓰지 않는 상수는 이유 표에 적는다). 같은 명령이 블록, 아이템, 레시피 표도 만든다(`data.md`).
- 생성 파일 첫 줄은 `// @generated by cargo xtask gen; do not edit.`이다. 생성 파일은 손으로 고치지 않는다. 틀린 출력은 생성기(`xtask/src/gen*`)나 IR 입력을 고친다.
- `cargo xtask gen --check`는 `target/`에 다시 만들어 커밋된 IR과 생성 파일을 바이트로 비교한다. `cargo xtask verify`가 맨 앞에서 이것을 돈다. Go가 PATH에 없으면 실패한다(시험도 같다).
- 이름(`xtask/src/gen/names.rs` 한 곳): 용어 표의 이름(`Http`, `Xuid`, `Uuid` 등)을 먼저 한 단어로 묶고, 나머지는 대소문자 경계로 나눈다(`HTTP|Server`). 숫자는 앞 단어에 붙인다. 모듈 이름과 겹치는 앞뒤는 뗀다(`packet::ViolationWarning`). 규칙에 맞지 않는 이름은 같은 파일의 예외 표에 적는다. Rust 키워드인 필드는 raw identifier(`r#type`)다.

### Rust 표현
- Go 구조체는 같은 모양의 평평한 struct다. 조건부 필드도 늘 있고 없으면 `Default`다. gophertunnel과 1:1이라 P3 판정과 버전업 비교가 단순하다. 더 나은 공개 모양은 상위 API가 감싼다. 모두 `Debug, Clone, PartialEq, Default`다.
- `Optional` → `Option`, 슬라이스 → `Vec`, 인터페이스 → enum, `mgl32.Vec3` → `[f32; 3]`, `uuid.UUID` → `Uuid`, NBT 컴파운드 → `BTreeMap<String, nbt::Value>`(바이트 순으로 쓰고 같은 키는 뒤가 이긴다: Go map과 같다), EntityMetadata → `BTreeMap<u32, _>`(gophertunnel도 키를 정렬해 쓴다).
- 문자열은 `String`이고 UTF-8이 아니면 디코드 오류다(gophertunnel은 검사하지 않는다). bool은 0과 1만 받는다. 쓰기는 길이를 조용히 자르지 않고 오류를 낸다(인코딩도 `Result`).
- NBT 목록(`nbt::List`)은 빈 목록도 원소 타입을 늘 지닌다. 그래서 모든 목록이 같은 바이트로 다시 쓰인다(gophertunnel은 빈 Int·Long 목록만 타입을 지키고 나머지는 End로 다시 쓴다). NBT는 중첩을 스레드 스택이 아니라 힙 스택에 두어 깊이와 무관하게 스택이 평평하다.
- 공개 범위: `anchor::protocol`은 공개 코덱 층이다(패킷과 타입, `Packet` 디코드·인코드, 배치 인코드·디코드, `Compression`). 패킷 훅이 패킷 값을 다루고 xtask 시험이 이 층을 부르기 때문이다. `Reader`, `Writer`, `Codec`은 `pub(crate)`다. NBT는 저장에서도 써서 `anchor::nbt`다.

### 손으로 쓰는 코덱
`protocol.IO`의 원시형이 아닌 메서드는 Marshal로 표현되지 않아 손으로 쓴다: 벡터·위치, UUID, 색, NBT(`src/nbt.rs`), EntityMetadata, ItemStack 계열, StackRequestAction 등 union의 태그 틀(`union_frame.rs`), GameRule, AbilityValue, Bitset, PackSetting, ShapeData, MaterialReducer, 이벤트 틀, 거래 데이터 틀, Login 요청 봉투(`protocol/login.rs`), 서브청크 페이로드(`block_storage.rs`). union의 변형 구조체와 ID 표는 생성하고 태그를 읽고 쓰는 틀만 손으로 쓴다.

### 배치 형식 (`protocol/batch.rs`)
- 패킷 머리 varuint32: ID는 0~9비트, 보낸 쪽 하위 클라이언트 10~11, 받는 쪽 12~13. 그보다 높은 비트는 읽을 때 무시한다(gophertunnel과 같고, 공식 클라이언트 출력은 관찰할 수 없어 받는 쪽을 넓힌다).
- 배치당 패킷은 812개 이하(gophertunnel 값)이고 BDS는 최대 45개를 보낸다. 출력은 256 KiB 전과 812개에서 배치를 끊는다. 압축 바이트와 해제 상한은 `network.md`에 있다.

## 디코드 상한
모든 디코드 상한은 `Reader::limit` 하나를 지나고 넘으면 크기 오류(`Error::Size`)다.
- 선언 길이는 남은 입력 이하. 목록 개수는 1024 이하(gophertunnel `maxSliceLength`, EntityMetadata 개수 포함)이고 남은 입력 이하.
- 할당 예산: Reader는 배치 하나마다 2 × `max-batch-bytes` 예산을 받고, 모든 `Vec`, `String`, NBT 할당이 `개수 × size_of`를 먼저 뺀다. 개수 상한만으로는 중첩 목록과 큰 원소가 입력 크기의 수십 배를 할당할 수 있어서다. 중첩 Reader는 같은 예산을 나눠 쓴다.
- NBT는 깊이 512(루트 포함), 루트 하나 4 MiB 이하.
- 필드별 상한: Mojang bedrock-protocol-docs JSON 스키마의 `maxLength`, `maxItems`, `maxProperties`를 쓴다.
  - `cargo xtask dump`가 고정 커밋의 스키마를 읽고, 스키마 항목을 gophertunnel 필드에 잇는 표(`xtask/src/dump/limits.rs`)로 `xtask/data/reference/protocol_limits.json`(필드 113개)을 쓴다. 문자열과 바이트는 바이트 수, 목록은 원소 수다. `[]`가 붙은 항목은 목록의 각 원소를 제한한다.
  - 스키마 상한이 표에 없거나 표 행이 스키마에 없으면 dump가 실패하고, 어떤 코덱에도 쓰이지 않는 상한은 gen이 실패한다. 그래서 버전업 때 생기거나 사라진 상한이 모두 드러난다.
  - gen은 상한을 디코더와 인코더 모두에 넣는다. 목록은 min(필드 상한, 1024)이다. 인코더도 같은 상한으로 오류를 내므로 Anchor가 클라이언트가 거부할 패킷을 보내지 않는다.
- 서브청크 페이로드 해제는 엄격하다: 비트 수 {0,1,2,3,4,5,6,8,16}만, 지속(persistent) 팔레트 플래그와 0x7f 거부, 팔레트 길이 ≤ 2^bits, 모든 인덱스 < 팔레트 길이.

## gophertunnel 결함과 조치
고정한 gophertunnel에서 찾은 결함이다. Anchor는 아래처럼 고치고, 같은 형식을 유지해야 하는 곳은 시험 표본을 맞춘다.
- MaterialReducer: gophertunnel Reader가 `mix << 16`으로 읽는다(`>> 16`이 맞다). Anchor는 `mix >> 16`, `mix & 0xffff`로 읽고 범위를 넘는 쓰기는 오류다. 코퍼스는 mix 0~0x7fff만 쓴다.
- Event 타입 8, 9, 10, 12, 14, 20, 21, 22는 ordinal이 없어 읽기도 쓰기도 안 되고, ordinal 21을 세 이벤트가 나눠 쓴다. Anchor는 ordinal 없는 이벤트를 쓰지 않고 오류로 낸다.
- 쓸 때 덮어쓰거나 읽고 버리는 값(ItemDescriptorCount aux 32767, StackRequestAction legacy 바이트, Skin `trusted`, 몇 패킷의 이름 문자열, InventoryTransaction `hasLegacy`)은 생성 코드가 gophertunnel과 같게 두고, 클라이언트 패킷을 처리하는 틱 코드가 검사한다.
- EntityMetadata 개수 상한 없음, NBT 깊이 계수 누수, 부분 읽기 허용, ItemInstance·Login 길이 조용히 자름: Anchor는 상한과 오류로 막는다.
- Snappy 해제가 `s2.Decode`라 S2 확장도 받는다: Anchor는 표준 Snappy만 받는다.
- 로그인 마감 없음, 지연 패킷 큐 상한 없음, 0xff 원문 상한 없음: Anchor 세션에는 모두 있다(`network.md`).

## 시험 P1~P5
Go 도구는 개발 때만 쓰지만 모든 시험은 `cargo test`로 돌고 `cargo xtask verify`에 들어간다(Go가 없으면 실패한다). P6(BDS 대조)는 `testing.md`에 있다.

- Go 오라클(`xtask/go/oracle`):
  - `corpus`: 무작위 값을 고르며 쓰는 `protocol.IO` 구현으로 각 패킷의 Marshal을 돌려 표본을 만든다(시드 고정 PCG, 목록 길이 0~4, `-limits`로 필드 상한 안 표본만). 평범한 gophertunnel Writer로 쓰고 패킷 최상위 NBT만 자체 정렬 인코더로 쓴다(Go map 순서가 무작위라서). gophertunnel Reader로 다시 읽어 성공한 표본만 남긴다. 코퍼스는 시험 때 `target/`에 만들고 커밋하지 않는다.
  - `check`: 받은 바이트를 gophertunnel로 디코드하고 다시 인코딩해 돌려준다. 바이트 비교는 Rust가 한다.
  - `compress`, `decompress`: gophertunnel `packet` 패키지의 zlib과 Snappy.
  - shield 아이템 ID는 양쪽 모두 고정값을 쓴다.
- P1 디코드 완결(`xtask/tests/protocol.rs`): 모든 패킷마다 코퍼스 표본 64개, 모든 표본에서 Rust 디코드가 성공하고 남는 바이트가 0이다. IR 패킷 수 = gophertunnel 두 풀의 합집합 = `Packet` variant 수(236)다.
- P2 왕복: 모든 표본 b에서 `encode(decode(b)) == b`. P4에서 디코드에 성공한 변형 m마다 `e = encode(decode(m))`이면 `encode(decode(e)) == e`(바이트 비교라 NaN에도 맞다).
- P3 gophertunnel과 양방향 일치: (가) Go가 만든 바이트를 Rust가 다시 인코딩하면 같다. (나) 변형의 Rust 인코딩 R → Go 디코드 → Go 재인코딩 → Rust 디코드 → Rust 재인코딩 == R. 차이는 빈 NBT 목록의 원소 타입 하나만 값 구조 비교로 허용한다. 배치 압축(`xtask/tests/compression.rs`)은 zlib과 Snappy 각각 Rust 압축 → Go 해제, Go 압축 → Rust 해제가 원문과 같다(크기 0, 1, 255, 256, 64 KiB, 1 MiB, 무작위와 반복 데이터).
- P4 변형 입력: 패킷마다 고정 시드 변형 1000개(비트 뒤집기, 바이트 넣기·빼기, 자르기, 길이 필드 키우기)에서 패닉 0. 상한마다(길이, 개수, 예산, NBT 깊이·크기, 해제 크기, 배치 패킷 수, 필드 상한) 넘는 선언이 크기 오류로 끝나는 시험이 있다. Snappy 결함 입력 5종과 zlib 폭탄은 오류다. 외부 입력을 읽는 다른 디코더(RakNet 데이터그램, 시그널링 요청, SDP, 피어)도 고정 시드 변형 1만 개에서 패닉 0을 시험한다.
- P5 봇 접속(`xtask/tests/spawn.rs`): gophertunnel `packet`, `login`과 go-raknet, go-nethernet으로 만든 Go 봇(`xtask/go/bot`)이 같은 프로세스에서 띄운 Anchor에 RakNet과 NetherNet, zlib과 Snappy 각각으로 스폰한다. 큰 스킨(해제 6 MiB) Login, 두 전송 동시 스폰, NetherNet 실패 때 RakNet 폴백, 로그인 마감과 로그인 전 상한, 신원 결합 불일치, 중복 로그인 두 경우를 본다. 온라인 로그인은 시험용 발급자(자체 키로 만든 OpenID 설정, JWKS, 토큰)로 검증하고 실제 Xbox 토큰은 쓰지 않는다. `xtask/tests/go.rs`는 Go 도구 자체의 시험을 돈다.

## 버전업 절차
새 프로토콜 버전으로 옮길 때 차례대로 한다. 단계마다 앞 단계가 통과해야 넘어간다.
1. 출처 고르기: gophertunnel의 새 정식 태그를 고른다(프리뷰 브랜치 금지). 태그 뒤 master의 커밋을 읽고 같은 프로토콜의 형식 수정이 있으면 그 커밋으로 고정한다. 그 go.mod의 go-raknet, go-nethernet을 따라간다.
2. 외부 불신 검토: 바뀐 Go 코드(`protocol`, `packet`, `login`, 압축, go-raknet, go-nethernet)를 직접 읽고 결함을 적고 없앤다(`dependencies.md`). 위 결함 목록이 아직 맞는지 다시 본다.
3. 고정: `xtask/go/go.mod`(와 `go.sum`)의 의사 버전을 바꾼다.
4. 생성: `cargo xtask gen`. 추출이 모르는 구문으로 실패하면 추출기를 넓힌다. IR diff(`xtask/data/protocol.json`)를 읽어 새·바뀐·사라진 패킷, 필드, union, 상수를 확인하고, 손 코덱과 이를 쓰는 엔진 코드를 맞춘다. 이름이 규칙에 맞지 않으면 예외 표에 더한다. 생성 파일은 고치지 않는다.
5. 필드 상한: Mojang bedrock-protocol-docs의 같은 버전 릴리스 커밋으로 `xtask/src/dump.rs`의 고정 값을 바꾸고 `cargo xtask dump`를 돈다. 생기거나 사라진 상한은 dump와 gen이 실패로 알리므로 `limits.rs` 표를 고친다.
6. 시험: P1~P5를 포함한 `cargo xtask verify`가 PASS해야 한다.
7. 데이터: 같은 버전의 PMMP, dragonfly, CloudburstMC 기준 목록으로 바꾸고 상태 대조와 업그레이드 스키마를 맞춘다(`data.md`). 인증 디스커버리는 `GAME_VERSION`으로 주소를 만들므로 함께 바뀐다.
8. BDS 대조: 새 버전 BDS의 복사본(`.cache/bds/<버전>/`)으로 P6 전체를 돌리고 다른 점은 BDS를 따른다(`testing.md`).
9. 표시: 공개 API의 깨지는 변경으로 버전을 올리고, 지원 프로토콜 번호와 고정 버전 표(이 문서)를 바꾼다.
