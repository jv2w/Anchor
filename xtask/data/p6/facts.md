# P6 facts

The values the pinned official server (`.claude/docs/protocol.md`) sends the bot, and what Anchor does about each. Only values that came out the same in two or more runs of the same scenario are written down. A value that differs per run is written as "random". The scenarios and the comparison are in `.claude/docs/testing.md`.

## Capture conditions
- Game scenarios: `cargo xtask p6 game official [trade]...` → `target/p6/official-game/`. RakNet, zlib, a new flat world.
- API scenarios: `cargo xtask p6 api official [scenario]...` → `target/p6/official-api/` (a `<scenario>.txt` report per scenario). The same conditions plus `allow-cheats=true` and the form script pack (`xtask/data/p6/forms-pack`).
- Spawn window: `cargo xtask p6 official` → `target/p6/official-<compression>/`.
- Block scenario (the RakNet run of `p6 official` and `p6 anchor`, `blocks.txt`): after the bot spawns and before the first step, the console command `gamerule randomtickspeed 0` turns random ticks off. Left on, placed blocks change by themselves between steps (the official server runs random ticks at the default 1, so a copper grate can oxidize). Anchor has no random ticks of vanilla blocks and needs no such step.
- Console at session start: `gamerule domobspawning false`, `gamerule dodaylightcycle false`, `gamerule doweathercycle false`, `kill @e[type=!player]`. Difficulty normal.
- Each scenario plays as a new player (`P6Trade` and so on) after a `tp` to its own area. The coordinates are absolute, so the same flat ground of both servers is compared as it is.
- World setup is console commands: `tp`, `give`, `setblock`, `fill`, `summon villager`, `effect`, `kill`. On Anchor's side the harness (`xtask/src/p6/game/console.rs`) translates the same commands to the public API.

## Loading screen and request IDs
- Until the client sends `ServerBoundLoadingScreen` (Start, End), the official server rejects every block click (UseItem ClickBlock) and sends the nearby blocks and the player state again. The bot sends both right after initialization.
  - Anchor: receives and drops this packet. It is no condition for rejecting anything.
- Request IDs: counting down by 2 from -1 like the client is accepted as is. Within one request, the StackNetworkID of a changed slot (the result slot 60:50, a slot emptied in the same request) is the request ID.

## Inventory requests (ItemStackRequest)
- Container numbers: with a window open, the inventory is 12 (CombinedHotBarAndInventory), the cursor 59, the created result 60 slot 50, the first trade ingredient 47:4. 60 never appears in a response.
- Response shape: `Status` 0, the changed slots in action order (source → destination, consumed slot → result slot). Per slot: `Slot` = `HotbarSlot`, the count, the StackNetworkID (0 for an empty slot), `CustomName` "", no `FilteredCustomName`, `DurabilityCorrection` 0.
- Stack network IDs (official server): one counter for the whole server. Moving a whole stack by request carries its ID along. Moving part of it gives an empty destination slot a new ID and leaves the source slot's. A slot whose count only changed, and a slot merged into, keep their ID. A trade result has a new ID. Changes outside requests (give, use of an item that shrinks the stack, pickup) give new IDs.
- Window IDs: per player, from 2, up by 1 on every open (the player's own inventory window and the trade window share the counter). Closing: client ContainerClose(window, the open type, false) → official server ContainerClose(same window, type 247 (= -9 NONE), ServerSide false).
- Resync after a block click: on every click that uses an item (placing), after the changed inventory (InventoryContent 0, 120, 124, 119, PlayerHotBar select false) and the block updates (the clicked block, the placed block, the blocks below and above), the official server sends the whole player state (all of UpdateAttributes, all of SetActorData, InventoryContent of 4 windows, PlayerHotBar select true) and the placed block once more. The same with client prediction actions.
- Console give: the official server sends a server → client InventoryTransaction (normal, two actions: container window 0 slot N empty → the item with a new ID, source 3 (creative) slot 1 the item → empty), InventoryContent of 4 windows, the sound `pop`, and Text (`commands.give.successRecipient`).
- Anchor: container numbers, the request ID rule, the stack ID rules within a request, and the response slot order are the official server's. The stack ID counter is per player. A slot whose count a container changed in its own tick keeps its ID (official server). After an item click (UseItem ClickBlock, ClickAir), when any of the player's own slots the client predicted (windows 0, 120, 119) differs from the server's slot (item, meta, count, tag), the 4 windows and the open window are sent again (once per tick). The client changes the slots ahead when it sends a click and keeps them until the server sends them again, so a rejected click left uncorrected puts the held count out of step with the server, and every later click is rejected. A click whose prediction was right, or that predicted nothing, gets nothing (a held click arrives every tick). The resend of the whole player state and give's InventoryTransaction are not copied (the comparison looks only at the resulting state).

## Breaking, drops, pickup
- Server-authoritative breaking: block actions `[StartBreak(position, face 1), PredictDestroyBlock(position, face 1)]` in one tick of PlayerAuthInput (InputFlagPerformBlockActions). Official server: LevelEvent 3600 (StartBlockCracking, data 65535), LevelEvent 2001 (ParticlesDestroyBlock, the block center, data = the runtime ID of the broken block), UpdateBlock air, drop AddItemActor (each with SetActorData and MoveActorDelta).
- Drop movement: the position of AddItemActor and MoveActorDelta is the feet + 0.125, MoveActorDelta `Ticks` 0, sent every tick while falling, unchanged axes absent (null). The MoveActorDelta of xp orbs and villagers also has `Ticks` 0.
- Pickup: when the item is inside the player's box, TakeItemActor(item runtime ID, player runtime ID) → server → client InventoryTransaction (normal: container window 0 slot N old → the new item with a new ID, source 2 (world) slot 1 the item → empty) → RemoveActor. No InventorySlot.
- Server-authoritative movement undoes the bot's walking with CorrectPlayerMovePrediction (the bot does not reproduce physics), so the bot stands on the drop by `tp`.
- Block action format: the official server accepts StopBreak and AbortBreak in gophertunnel's format (position and face on every action). StartItemUseOn or StopItemUseOn in PlayerAuthInput block actions makes the official server drop the connection without a Disconnect.
- Anchor: drop position, `Ticks`, and sending every tick are the official server's. Pickup may be announced differently (the comparison looks at the resulting state). Block actions are read in gophertunnel's format; an unknown action or face drops only that packet's block actions.

## Trading and villagers
- Summoning: the console command `summon villager x y z 0 0 minecraft:become_farmer name` makes an adult farmer villager_v2 (Variant 1, SkinId 0; a command name `villager_v2` is a syntax error). The command's event replaces the default spawn event (random profession, 5% babies, nitwits included, random SkinId). `minecraft:spawn_farmer` picks one of farmer, fisherman, shepherd, fletcher, and mason at random. The bot adds `become_farmer` to both summons of `trade` and `tradeup` (`summon villager` and the legacy `summon minecraft:villager`) to fix the profession: with a random profession the first tier may hold no offer the bot can pay (fisherman: string → emerald, emerald + cod → cooked cod) or no trades at all (baby, nitwit), and the steps differ per run.
- Locked offers: the official server also grants, with status 0, a trade request for an offer whose `tier` is above the villager's `TradeTier` (the tier 2 offer "10 emeralds → enchanted fishing rod", `traderExp` 10, of a TradeTier 0 fisherman). That xp raises the villager to tier 1 at once (reopened, UpdateTrade `TradeTier` 1), and the xp orbs of the trade that raised the tier total 11, more than an ordinary trade (3 to 6), so the player reaches level 1. The official client cannot pick a locked offer, so the bot also picks only offers at or below `TradeTier`. Anchor refuses a trade of a locked offer (`tick/trade.rs`).
- `summon minecraft:villager` also arrives as AddActor type `minecraft:villager_v2`. The official server has no legacy actor, and that villager's Trade2 window opens normally too.
- Opening: InventoryTransaction UseItemOnEntity(Interact, villager runtime ID) → no ContainerOpen; UpdateTrade (window from 2, `WindowType` 15, `Size` 0, `TradeTier` 0, `VillagerUniqueID` the villager's unique ID, `EntityUniqueID` -1, `DisplayName` "entity.villager.<profession>", `NewTradeUI` true, `DemandBasedPrices` true) → InventoryContent (the trade window, an empty list), Event EntityInteract (`EntityRuntimeID` = the player's unique ID, UsePlayerID true, InteractionType 7, InteractionEntityType 115, InteractedEntityID the villager's unique ID, EntityVariant the profession number), villager Animate.
- Offer NBT: root `{Recipes: list, TierExpRequirements: [{"0":0},{"1":10},{"2":70},{"3":150},{"4":250}]}` (each element one int whose key is the tier as a string). Each offer: `buyA` (compound: `Count` byte, `Damage` short (32767 = any meta), `Name` string, `WasPickedUp` byte, `Block{name, states, version}` for a block item), `buyB` (same shape, only when present), `buyCountA` int (= `buyA.Count`), `buyCountB` int, `demand` int, `maxUses` int, `netId` int, `priceMultiplierA` and `B` float (0.05, 0.2 for expensive ones), `rewardExp` byte (1), `sell` (same shape, plus `tag{ench:[{id,lvl}]}` when enchanted), `tier` int (0 to 4), `traderExp` int, `uses` int. The offers of every tier are there from the start; `TradeTier` sets which tiers are open.
- Trade requests (status 0): payment `[Place(buyCountA, 12:slot, 47:4 ID 0)]` → response [12:slot, 47:4 new ID]. Trade `[CraftRecipe(offer netId, 1), CraftResultsDeprecated([sell], 1), Consume(buyCountA, 47:4), Place(sell count, 60:50 ID = request ID, 12:slot)]` → response [47:4 x0, 12:slot result new ID].
- `DemandBasedPrices` is always true. A new villager's `demand` is 0 and stays 0 after trades. Demand changes only when the villager restocks at its workstation (mob AI).
- After a trade the official server sends no new UpdateTrade (the client applies it itself). When the tier rises with the window open (0 → 1 at the 10th trade), it sends only the villager's SetActorData (101 TradeTier). Reopened, only the traded offer has `uses` +1; prices, demand, and multipliers are unchanged. As the reward it summons xp orbs (a random count) at the villager's position, and several villager SetActorData follow (trade xp, animation).
- Villager metadata: AddActor `villager_v2` with 101 TradeTier 0, 102 MaxTradeTier 4, 103 TradeExperience 0, 104 SkinId (random with the default spawn event, 0 and 4 seen; 0 with a `become_farmer` summon). SetActorData after a trade holds only the changed keys (such as `{103: 5}`).
- Profession numbers (official server `behavior_packs/vanilla` villager_v2): 0 unemployed, 1 farmer, 2 fisherman, 3 shepherd, 4 fletcher, 5 librarian, 6 cartographer, 7 cleric, 8 armorer, 9 weaponsmith, 10 toolsmith, 11 butcher, 12 leatherworker, 13 mason, 14 nitwit. The Variant and the trade window title of a summoned villager match this table (3 → `entity.villager.shepherd`, 7 → `entity.villager.cleric`).
- Closing: client ContainerClose(window, 15, false) → official server ContainerClose(window, 247, false).
- Anchor: the actor type of a villager-like NPC is `minecraft:villager_v2` alone; the close answer is 247. The window type, the offer NBT keys, `netId`, and UpdateTrade after a trade are the trade protocol values of `.claude/docs/architecture.md`. Metadata 101 to 104 are the official server's keys, with SkinId fixed at 0. The profession table (`trade.rs`) is the official server's. Without villager AI, demand is always 0. No Event EntityInteract is sent for trading (statistics; no effect on the client).

## Spawn window
- Order: NetworkSettings → ServerToClientHandshake → PlayStatus(0) → ResourcePacksInfo → ResourcePackStack → LevelEventGeneric → PlayerList → SyncWorldClocks → JigsawStructureData → VoxelShapes → StartGame → SyncActorProperty ×13 → ItemRegistry → (RequestChunkRadius) → SetSpawnPosition → SyncWorldClocks → SetDifficulty → SetCommandsEnabled → UpdateAdventureSettings → UpdateAbilities → GameRulesChanged → PlayerList → UpdateAbilities → BiomeDefinitionList → AvailableActorIdentifiers → PlayerFog → CameraPresets → CameraAimAssistPresets → CameraSpline → UpdateAttributes → CreativeContent → TrimData → InventoryContent ×4 → PlayerHotBar → CraftingData → AvailableCommands → Respawn ×3 → (chunks) → LevelSoundEvent → SetActorData → CurrentStructureFeature → UpdateAttributes → ChunkRadiusUpdated → (AddActor of nearby mobs and the like) → SetHealth → PlayStatus(3).
- LevelEventGeneric: EventID 9801 (SleepingPlayers), data = the contents of a network NBT compound without its root tag (three ints and the closing 0): `ableToSleep` 1, `overworldPlayerCount` 1, `sleepingPlayerCount` 0 (one player).
- PlayerList (twice, same contents): ActionType Add, one entry (the player): UUID, EntityUniqueID, Username, XUID "", PlatformChatID "", BuildPlatform 1, the whole skin, Teacher, Host, SubClient false, PlayerColour {237,237,237,255}.
- SyncWorldClocks: the first PayloadType 0 (SyncStates [{ClockID, Time, Paused false}]), the second PayloadType 1 (Clocks [{ID, Name "minecraft:overworld", Time, Paused, 6 TimeMarkers: sunrise 23000, night 13000, noon 6000, midnight 18000, day 1000, sunset 12000, all with Period 24000}]). The marker IDs are fixed values.
- VoxelShapes: NameMap 220, Shapes 287, CustomShapeCount 0, 23,178 bytes encoded. Count, name order, and size equal the reference list's `voxel_shapes.json` (`xtask/data/reference/`). Anchor sends that file.
- 13 SyncActorProperty: the property definitions of zombie_nautilus, wolf, sulfur_cube, chicken, creaking, pig, cat, egg, armadillo, happy_ghast, copper_golem, bee, cow. The order and contents of the Windows official server equal the reference list's `entity_properties.dat`. Anchor sends that file.
- AvailableActorIdentifiers: 8,907 bytes, byte for byte the reference list's `entity_identifiers.dat`. Anchor sends that file as it is.
- JigsawStructureData: without it the official client disconnects with `disconnectionScreen.missingStructureData`. Anchor sends the contents of the reference list's `jigsaw_structure_data.dat` in the official server's place.
- CameraPresets (6 presets: first_person, fixed_boom, follow_orbit, free, third_person, third_person_front), CameraAimAssistPresets (categories bucket, empty_hand, default; one preset), CameraSpline (an empty list): Anchor sends the Windows official server's contents (`xtask/data/reference/camera.json`) in the same place.
- The Windows and Linux official servers send the same contents, but the order of the lists below differs. Each build keeps its order over repeated runs. All are lists the client looks up by name, so their order carries no meaning, and P6 compares them in key order (`in_key_order` in `xtask/src/p6/compare.rs`, `sortByIdentifier` of `bot worlddata`).
  - The entity type order of the SyncActorProperty packets (Linux: sulfur_cube, wolf, armadillo, pig, happy_ghast, cat, creaking, zombie_nautilus, chicken, bee, egg, cow, copper_golem). The order of one entity's `properties` list is the same in both builds and carries meaning: AddActor's EntityProperties point at a property by its number in that list (`Index`) (the official server's chicken AddActor `IntegerProperties` Index 0 and 1, gophertunnel `IntegerEntityProperty`). So that list is compared in order.
  - The category order of CameraAimAssistPresets (Linux: empty_hand, default, bucket) and the order of each category's `Blocks` priority list (bucket: Windows cauldron, lava, water; Linux cauldron, water, lava). Presets point at categories by name (`ItemSettings.Category`, `DefaultItemSettings`, `HandSettings`), and there is one priority per block name.
  - The order of the 64 JigsawStructureData `template_pools`. The four top-level lists (jigsaws, processors, structure_sets, template_pools) are definitions named by `description.identifier` that point at each other by name (`start_pool`, `structure`). The lists inside a definition (the weighted `elements` and the like) have the same order in both builds and are compared in order.
  - Anchor: sends the Windows order (the reference list files' order). Anchor's AddActor sends EntityProperties empty and uses no property numbers.
- SetDifficulty 2 (normal, the configured value). UpdateAdventureSettings {NoPvM false, NoMvP false, ImmutableWorld false, ShowNameTags false, AutoJump true}. UpdateAbilities (twice, same values) {EntityUniqueID the player, PlayerPermissions 1 (member), CommandPermissions 0, Layers [{Type 1 (base), Abilities 1048575, Values 63, FlySpeed 0.05, VerticalFlySpeed 1, WalkSpeed 0.1}]}.
- SetCommandsEnabled: false with `allow-cheats=false`, true with true. Anchor always sends true (it has no cheats concept).

The other bools are true.
- The first UpdateAttributes (Tick 0), 17 attributes: player.hunger 20/0 to 20, saturation 5, exhaustion 0, level 0/0 to 24791, experience 0/0 to 1, health 20, follow_range 16/0 to 2048, knockback_resistance 0/-2 to 1, movement 0.1, underwater_movement 0.02, lava_movement 0.02, attack_damage 1/1 to 1, absorption 0/0 to 16, luck 0/-1024 to 1024, friction_modifier 1/0 to 256, bounciness 0/0 to 1, air_drag_modifier 1/0 to 256 (Default = the value, no modifiers). - After SetLocalPlayerAsInitialised comes UnlockedRecipes (type 1, 20 recipes), outside the window. Anchor has no recipes and does not send it.

## Commands
- Player commands are sent as CommandRequest (origin `player`, a new UUID, RequestID "", PlayerUniqueID 0, Internal false, Version `"latest"`). The official server accepts this form.
- AvailableCommands (member): the official server sends all 82 commands whatever the permission (PermissionLevel 0: 4, 1: 60, 2: 7, 3: 1, 4: 10). The client hides them by its own permission. Order: SetCommandsEnabled after SetDifficulty, AvailableCommands after CraftingData.
  - Anchor: sends only the commands the player is allowed. So after op and deop it sends AvailableCommands again.
- Parameter type numbers: int 1, float 3, target 8, string 56, position 65, message 68 (MessageRoot: kick), raw_text 70, json 74. gophertunnel's `CommandArgTypeMessage` is 67. Anchor uses the observed 68.
- Official server command shapes (permission level, flags, overloads): give 1 0 `target enum:Item int? int? json?` / gamemode 1 0 `enum:GameMode target?`, `int target?` / kick 1 128 `target message` / op 2 1152 `target` / tp is an alias of `teleport`.
- A command without aliases has AliasesOffset 0xFFFFFFFF. The alias enum is `<name>CommandAliases`, with the name first (`teleport`: `["teleport","tp"]`, `allowlist`: `["allowlist","whitelist"]`). Anchor does the same.
- Among Anchor's built-in commands, give, gamemode, tp, kill, clear, kick, op, deop, list, and stop have the official server's argument types, names, and enums. `whitelist` follows the dump's command shape and differs from the official server. The command list comparison looks only at the commands both have, as notes.
- op: after the console `op <name>` the official server sends no new AvailableCommands but Text (type 10, rawtext `commands.op.message`) and UpdateAbilities (CommandPermissions 1, PlayerPermissions 2, one layer with Abilities 1048575, Values 255, FlySpeed 0.05, WalkSpeed 0.1, VerticalFlySpeed 1).
  - Anchor: op gives CommandPermissions 1, PlayerPermissions 2, and OperatorCommands and Teleport in Values (255 in survival); deop gives 0, 1, 63. An op to the same state sends nothing. An op player joins with op values from StartGame `PlayerPermissions` on.
- CommandOutput in general: the origin is the request's (Origin 0 player, the same UUID, RequestID "", PlayerUniqueID 0), OutputType 3 (AllOutput), no DataSet. On success SuccessCount 1 and a message with Success true; on failure 0 and false. Messages are translation keys with parameters.
- Official server values per command:
  - No permission (a member's `gamemode creative`): `commands.generic.error.permissions` `["gamemode"]`. The command is in the list, so it is not "unknown command".
  - `give @s stone 3`: `commands.give.success` `["Stone","3","P6Commands"]`. To the receiver: Text (type 10, rawtext `commands.give.successRecipient` `["Stone","3"]`), InventoryTransaction, InventoryContent of 4 windows, PlayerHotBar, the sound `pop`.
  - `tp ~ ~1 ~`: `commands.tp.success.coordinates` `["P6Commands","-3.50","-59.00","-11.50"]` (feet coordinates, two decimals). MovePlayer (Mode 2 Teleport, TeleportCause 3, eye height +1), Text (type 10, `commands.tp.successVictim` `["-3.50, -59.00, -11.50"]`). A bot left floating soon gets CorrectPlayerMovePrediction.
  - `gamemode creative`: `commands.gamemode.success.self` `["%createWorldScreen.gameMode.creative"]`. Only UpdatePlayerGameType (GameType 1, PlayerUniqueID the player, Tick the server tick), no SetPlayerGameType or UpdateAbilities. Text (type 10, `gameMode.changed` `["%createWorldScreen.gameMode.creative"]`).
  - `give @s no_such_item`: `commands.generic.syntax` `["/give @s ","no_such_item",""]`.
  - `no_such_command`: `commands.generic.unknown` `["no_such_command"]`.
- Syntax error `commands.generic.syntax` [before, the wrong word, after]: before is at most 10 characters before the wrong word on the line counted from `/`, after at most 10 characters after the word (`/give @s no_such_item 3 and more words` → `["/give @s ","no_such_item"," 3 and mor"]`). With an argument missing, the word is "" and before is the 10 characters before the line end (`/give @s` → `["/give @s","",""]`). With several overloads, it is the place matched furthest.
- The official server sends an Event (SlashCommandExecuted: the command name, success count, message count and keys) for every command (telemetry). Anchor does not.
- What Anchor does as the official server does: unknown commands, no permission (also for a `/` line typed in chat), the keys and parameters of syntax errors (`command::Error::Syntax`), the game mode name `%createWorldScreen.gameMode.<mode>`, Text 10 to the player a command touched (`gameMode.changed` also to the player itself, `commands.give.successRecipient`, `commands.tp.successVictim`), two decimals in tp coordinates, UpdatePlayerGameType after gamemode only to the changed player (no SetPlayerGameType, also for the hardcore spectator switch; sent with another player's ID, the client ignores it), the order and values of `effect clear`.
- What Anchor does differently on purpose (`intended.txt`):
  - The item name in give's success message: Anchor writes the ID (`minecraft:stone`). It has no table of item display names.
  - UpdateAbilities after gamemode: it must carry the flying, collision, fly speed, and op values the API changed, and with the same values it does the client no harm.
  - `/gamemode` to the current game mode fails (the official server succeeds).
  - UpdatePlayerGameType `Tick`: the server tick on the official server (such as 333), 0 on Anchor (not a compared field).

## Chat and string limits
- For a client Text (Chat), the official server sends everyone a Text (type 1 Chat, SourceName `name§r`, Message as written, no Parameters, NeedsTranslation false).
  - Anchor: with PlayerChat's format at its default (`None`), the official server's shape. When a listener gives a format, that text goes out as Raw. Receivers and the words follow the event. When the display name exceeds the chat source limit (256 bytes), the line goes out as the `chat.type.text` translation (Text type 2 Translation, [name, message], NeedsTranslation true) so it is not lost.
- The chat line limit is in bytes: the official server relays up to 512 bytes. ASCII 512 passes, 513 does not. 170 Hangul characters (3 bytes each, 510 bytes) pass, 171 (513 bytes) do not. A longer line is dropped without disconnecting. A raw Text of 65,538 bytes (21,846 characters) is dropped too, and the connection stays.
  - Anchor: a chat line limit of 512 bytes.
- CommandRequest lines: processed up to 507 bytes; from 508 bytes the official server drops the connection without a Disconnect (also a 600-byte unknown command). A Hangul line of 519 bytes (179 characters) is dropped too. The unit is the byte (the `line<bytes>` and `linekorean<bytes>` scenarios).
  - Anchor: the decoder unit (bytes) is the same. It does not disconnect, and answers `TooLong` at the limits of 512 characters and 2,048 bytes. The official client never sends such long lines, so answering is the safer side. These scenarios record facts.

## Forms
- The script pack for the official server (`@minecraft/server-ui` 2.0.0, no experiment toggles): `xtask/data/p6/forms-pack`. `/scriptevent p6:<kind>` sends a form to everyone. It is turned on by `development_behavior_packs/p6_forms` and `worlds/p6/world_behavior_packs.json`. Both ActionFormData and ModalFormData have `header`, `label`, and `divider`.
- Modal: `{"type":"modal","title","content","button1","button2"}`. The answer is true or false; closing gives a CancelReason.
- Menu: `{"type":"form","title","content","elements":[...]}`. Elements are buttons `{"type":"button","text","image":null}` or with `"image":{"type":"path","data":"textures/items/apple"}`, `{"type":"header","text"}`, `{"type":"label","text"}`, `{"type":"divider","text":""}`. There is no `buttons` key. The answer is the index counting buttons only.
- Custom: `{"type":"custom_form","title","icon":null,"content":[...]}`. Elements are header, label, divider (the menu's shapes), `{"type":"input","text","placeholder","default"}`, `{"type":"toggle","text","default"}`, `{"type":"slider","text","min","max","step","default","timeout":100}`, `{"type":"dropdown","text","options","default"}`. Numbers are written as floats like `10.0` (an integer default as `3`). The answer has one value per element (null for header, label, divider).
- Anchor: sends the same JSON (`"image":null` for a button without an image, `"icon":null`, the slider's `"timeout":100`). Keys are in name order (a JSON object; the client does not look at the order).

## Weather and lightning
- Reproduction: `cargo xtask p6 api official weather joinrain joinstorm`; lightning per difficulty with `boltpeaceful bolteasy bolthard`.
- Weather events are LevelEvent (position 0,0,0): rain start 3001, thunder start 3002, rain stop 3003, thunder stop 3004. Starts have data 65535, stops 0. No GameRulesChanged or other packet.
- The official server raises and lowers the rain and lightning levels over about 5 seconds, and the events a command sends follow the level at that moment (`weather thunder` before the level is fully up sends 3001 again, and `weather clear` while a thunder level remains also sends 3004).
- Once the levels have settled (7 seconds per step), only changes are sent: clear → rain 3001, rain → rain nothing, rain → thunder 3002, thunder → thunder nothing, thunder → rain 3004, rain → clear 3003, clear → thunder 3001 and 3002, thunder → clear 3003 and 3004, clear → clear nothing. Anchor has no level changes and uses this table (`src/tick/weather.rs`).
- Joining: StartGame `RainLevel` and `LightningLevel` are the levels at that moment (settled: rain 1 and 0, thunder 1 and 1). Right after SetCommandsEnabled in the spawn window, rain sends 3001 (data = rain level × 65535) and thunder only 3002 (data = lightning level × 65535). Clear sends nothing. A join before the levels are fully up gets values in between, like 0.85 and 55704. Anchor sends the settled values.
- `summon lightning_bolt x y z` (integer coordinates): AddActor `minecraft:lightning_bolt` at the bottom center of the block (x+0.5, y, z+0.5) with default metadata (flags 0). The SetActorData of the same batch has flag 0 (on fire) on in some runs and lacks the key in others. The next batch brings the fire block (UpdateBlock or UpdateSubChunkBlocks, `minecraft:fire` age 0) and LevelSoundEvent `thunder` and `explode` (EntityType `minecraft:lightning_bolt`, EntityUniqueID = the bolt, ExtraData -1). RemoveActor comes 20 to 40 ticks after the strike.
- A survival player 2 blocks from the bolt: on the strike tick health 20 → 15 (5 damage, ActorEvent hurt data 24 = lightning) and the on-fire flag, then 1 fire damage every 20 ticks. Fire starts on the struck block and at a few random places within 1 block around it (up to 4 seen). Beyond 8 blocks there is no damage.
- Difficulty: the 5 damage and setting on fire are the same in peaceful, easy, normal, and hard. Block fire is absent in peaceful and easy (0 block updates) and starts in normal and hard. Java Edition also burns only in normal and hard.
  - Anchor: lightning starts no fire (no block updates).
- During thunder the official server strikes random lightning near players (seen once in two 7-second steps). Anchor has no natural weather and no natural lightning.
- In rain the official server puts out burning players (fizz sound, LevelEvent 2029). Anchor implements no game effects of rain.
- Comparison: the bot's `weather` check (event order and data; bolt type, position, sounds, removal, fire, damage, on fire) and the `weather at join` check. The bolt's on-fire flag and random lightning are not compared.

## Entities and metadata
- Other players' movement: the official server sends walking, turning in place, and looking up all as MovePlayer mode 0 (not MoveActorDelta). tp is mode 2. Movement after a respawn is also mode 0.
  - Anchor: on a tick where the position or rotation changed, sends `MoveActorAbsolute` (eye position, ground flag, rotation [pitch, yaw, yaw]). The client interpolates, so nothing stutters. MovePlayer is used only for corrections of the player's own position and for teleports (mode 2) (`intended.txt`). A teleport's ground flag and mode 2 waver on both servers with the input's arrival time and are not compared.
- Another player's AddPlayer: the key set is that player's own 73 SetActorData keys + 10 (u8 0), 38 (f32 1), 53 and 54 (f32 width and height), 56 (Vec3 0), 74 (u8 0), 139 (i64 0) = 80 keys. The flags are the state at that moment (a player who just joined has no Breathing, one already there has it). GameType 5; BuildPlatform and DeviceID are that client's values; the ability layer is base (a player still loading gets one more layer, Type 5 loading screen). PlayerIndex (27) is the join order (1, 2). The player list color is #EDEDED for the first player and #54FFFF for the second.
  - Anchor: sends the official server's key set, types, and device values. Differences: no loading screen layer, and every list color is #EDEDED. Human NPCs have no counterpart on the official server.
- Metadata types: 136 int32, 137 int32, 138 int32, 139 int64 (only in another player's AddPlayer), 140 float32. 127 (the last death position) is a BlockPos, 133 (the position a bed was entered) a Vec3. Anchor does the same.
- AddActor of a lingering regeneration potion cloud: 61 radius 3.0, 8 color, 63 particle 35, 95 duration 600, 98 radius per pickup -0.5, 99 pickup count 0 (int32), 97 0.00083333, 36 potion ID 28 (int16), flags HasGravity+FireImmune, and the keys every actor has.
  - Anchor: does not send 9, 62, 96; 63, 95, 98, 99 are the official server's values. 97 stays 0 and the server sends the shrinking radius. 36 is not sent, since the cloud holds no potion ID.
- Locator bar: when another player comes into view, PlayerLocation{Type 0, that player, eye position}, a LocatorBar add {Action 1, UpdateFlag 63, color = that player's list color, IconSize 0.2, `textures/ui/locator_bar_dot_3`, position authority server, visible}, soon an update {Action 3, UpdateFlag 44, position authority client, IconSize 1, `locator_bar_dot_0`}. On death PlayerLocation{Type 1 hide} + an update {UpdateFlag 2, Visible false}; on respawn an update {UpdateFlag 2, Visible true}; on leaving a removal {Action 2, UpdateFlag 0}. GroupHandle is a UUID the official server chose. Anchor sends the same.
- Damage causes (ActorEvent hurt data): attack 2, projectile 3, drowning 9, lightning 24. Anchor carries the official server's numbers.
- Critical hits (the `others` mover jumps and hits while falling): the official server sends Animate{ActionType 4 CriticalHit, Data 55 (the star count)} for the hit player to the attacker and the hit player (twice, the same). With Data 0 the client draws no stars. Anchor carries 55 too. Magic critical hits (ActionType 5) were not seen on the official server; Anchor carries the dump's default 15.
- To the dying and respawning player itself: on death Respawn (State 0, the eye position where it died, EntityRuntimeID 0); for its Respawn(ClientReadyToSpawn) Respawn (State 0, position (0,32767,0)) and Respawn (State 1, the respawn eye position); for its PlayerAction(Respawn) ActorEvent 18 → SetHealth 20 → UpdateAttributes → SetActorData{0 flags (with Breathing), 53, 54}. Breathing is on right after the respawn. Anchor does the same, with its own MovePlayer (teleport) before ActorEvent 18 and its abilities and inventory after UpdateAttributes. A respawn through the API (no counterpart on the official server) first sends Respawn (State 1, the respawn eye position), which the client would otherwise wait for on its death screen, and a Respawn(ClientReadyToSpawn) from a player already back is answered with its eye position.
- The box size (53, 54) of a player who dies and respawns: on death SetActorData{127, 129, 53 0.2, 54 0.2}, on respawn SetActorData{53 0.6, 54 1.8} after ActorEvent 18, to the player and to every viewer. The client keeps a dead player's small box until these keys come, so without them viewers see the respawned player with a small hitbox and a low name tag. Anchor sends the same values (on death, 53 and 54 go in a different SetActorData from 127 and 129).
- Other players' attributes: when a player attribute changes, the official server also sends UpdateAttributes to viewers. On a hit the health (such as 19), on healing 20, on death health 0, on respawn all of health, hunger, exhaustion, saturation, level, and experience. Exhaustion from walking or hitting goes out too.
  - Anchor: to viewers only the health, on every change (the health value is the official server's). Hunger, exhaustion, saturation, and xp are shown only to the player. Sent to viewers too, each movement of those values would cost one more packet per viewer.
- Firework (no explosions, Flight 1): 16 `{Fireworks:{Explosions:[], Flight:1}}`, 17 Vec3 `[0,1,0]`, 18 int64 -1, 5 (owner) -1. Even without explosions it bursts with ActorEvent 25 (data 0). Anchor does the same (Flight computed from the flight time).
- End crystal (`summon ender_crystal`): 47 BlockTarget `[0,0,0]`, flag FireImmune. Anchor has the same 47.
- Trident: ActorEvent 2 data 3 (projectile) to the hit villager. The trident bounces back along x (MoveActorDelta positions) and falls to the ground after `item.trident.hit`. Anchor bounces it too.

## Item use
- Reproduction: `cargo xtask p6 api official itemuse` (bot `xtask/go/bot/itemuse.go`). On Anchor's side only the check lines are compared.
- Official client order (bedrock-protocol-docs changelog 776 `StartUsingItem`, gophertunnel `InputFlagStartUsingItem`): an item with a use action starts with InventoryTransaction UseItem ClickAir and the `StartUsingItem` flag of the same tick's PlayerAuthInput. Bows and tridents end with InventoryTransaction ReleaseItem. Thrown items are ClickAir alone.
- Official server: UsingItem on while drawing a bow or trident, off on release. On while drinking a potion; the official server ends drinking by its own clock (CompletedUsingItem).
  - Anchor: turns UsingItem on for eating, drinking, bows, tridents, goat horns, and spyglasses. Drinking ends with the second ClickAir after the use duration (same effects and bottle).
- Trident throw sound: `item.trident.throw` (data -1) at the thrower's feet + 0.9 (the body center). Anchor does the same. The official server then also sends the `disappeared` and `reappeared` sounds on the trident entity (arrows too). Anchor does not.

- Holding right click (official client, observed by the user in adventure mode; the bot cannot see this):

  - ClickAir (snowball) has trigger `Unknown`, and an entity Interact does not repeat while held.

- The totem of undying screen animation (shown only by the official client, which the bot cannot see, so unchecked; see "Real-client checks" at the end): the client is believed to draw the screen animation for an ActorEvent TalismanActivate (data 0) on its own runtime ID only while a totem of undying is in hand.   - Anchor: `Player::show_totem_animation` sends these three to that player alone. When a vanilla totem saves a player, the event goes to every viewer with the totem still in hand.
- Flight: with the same aim, the official server's splash potion hits the 3.5-block wall at height 1.6 and Anchor's hits the ground (apparently a difference in throw angle and force). ## Sneaking
- Reproduction: `cargo xtask p6 api official sneak` (bot `xtask/go/bot/sneak.go`). Only the check lines are compared.
- Official server: for every `StartSneaking` and `StopSneaking` of PlayerAuthInput it sends the player SetActorData{0 flags (Sneaking), 54 height 1.49 or 1.8} and SetActorData{92 flags}, and the `Tick` of both packets is the `Tick` of the input that carried the toggle (two answers even when it stops the next tick). Values the server changed by itself (such as Breathing) have `Tick` 0. The client rewinds an answer with a `Tick` to that input's frame and applies it there (bedrock-protocol-docs `PlayerMovementOverview`). With `Tick` 0 it applies it on arrival, so a late answer turns an already stopped sneak back on.
  - Anchor: the player's own SetActorData answering a toggle of the input (accepted or refused) carries the `Tick` of the tick's last toggle input; to viewers it is 0. The height goes as 54, as on the official server, and 130 (the collision box) stays the standing box of the spawn, [0.6, 1.8, 0]. Sending the sneaking height as 130 makes the real client sneak by itself, without shift, when jumping under a ceiling. Both flag words go in one packet. The official server also turns on Blocking (72) of the 92 word when sneaking. Anchor does not.
